## 1. Design overview

This document defines the wire protocol for syncing session files between A and B. The entire protocol can be stated in one sentence:

> **A does not track session content, only a position. That position is called a cursor, generated by B, shaped like `zpc1.<byte count>.<prefix fingerprint>`. A hands it to B to ask "am I behind?", and B answers with one of four results in a single response: no change, new bytes (with a delta), your copy is void — start over (with a full body), or B has no such session (404). A newly created fork session is delivered to B once via a second operation, `publish`.**

Breaking that sentence down gives four parts, each with its own section below:

- **Sync unit** (§4): what is transferred is not "records" but the **stable prefix** of the B file — the raw bytes from the start up to the last newline, copied verbatim on the A side.
- **Progress credential** (§5): a cursor is one encoding carrying two things — which byte I have received up to, plus what that byte content is (the fingerprint).
- **`changes`** (§6): a read operation. Pass a cursor, get one of four replies back.
- **`publish`** (§7): a write operation. Hand the fork product to B; identical bytes get an idempotent acknowledgment, different bytes get a 409.

Above these four parts runs one invariant that spans the whole protocol, and every rule exists to maintain it: **the local prefix that A has verified is byte-identical to the first N bytes of the B file** (N = cursor byte count). Every judgment, every write pattern, and every error code in the protocol answers "does the invariant hold at this moment, and how do we restore it".

## 2. Problem and constraints

zonepair splits a coding agent's model driver across two machines: A runs the opencode harness, B runs the real `claude`. Session files are produced and grow on B; A needs a local copy for session recognition, resume, and fork.

The shape of the protocol is squeezed out by four hard constraints:

1. **Zero patches to opencode**. The adapter cannot be modified — we cannot insert a sync before "read session info". So "data must be fresh" can only be expressed as "already in place at the moment of read"; sync must be driven continuously in the background, not intercepted on demand.
2. **A is nearly stateless**. Persistence is compressed to the minimum; anything that can be asked of B is not stored on A, anything that can be computed on the fly is not persisted. This directly determines that the progress credential must be self-contained — A stores only one string, and all semantic judgment happens on B.
3. **Normal session WS startup does not wait**. Sync cannot appear on the hot path; the only sync wait allowed is the publish wait of a fork resume, because that wait itself is a correctness condition.
4. **Crash recoverable**. The process can die at any time; the write ordering must ensure that "a crash" produces only recoverable residue, not semantic errors.

There is also a factual constraint: **B rewrites whole files** (merge overwrites the whole file, claude is an external writer with no hook). So "the first N bytes never change" has no mechanism guaranteeing it — length, mtime, and the uuid set all fail as consistency criteria. This is the direct reason §5 fixes the fingerprint as the sole criterion.

## 3. Terminology

| Term | Definition |
|---|---|
| Session file | A JSONL transcript file for one session, one JSON record per line |
| mirror | The directory tree on the A side holding copies of session files |
| Newline-terminated boundary | The byte position after the last `\n` found scanning backward from the end of the file, denoted `boundary`; `[0, boundary)` is called the **stable prefix** |
| Fingerprint | SHA-256 computed over a raw byte range, taking the first 16 bytes of output rendered as 32 hex characters |
| cursor | An opaque progress credential generated by B; encoding in §5.2 |
| Append | Appending a byte range at the end of a local file |
| Whole-file replacement | Replacing the local file wholesale via a same-directory temp file + atomic rename |
| B-managed | The authoritative party for a file is B: the A-side copy may only be written by the sync process; any local append or rewrite is illegal |
| A-managed | The authoritative party for a file is temporarily A: the state of an A-created fork product before `publish` confirmation |
| Tombstone | A persistent record of a deletion fact, bound to the content fingerprint of the deleted file instance, used to suppress resurrection |
| fork product | A new session file written out by the A-side SDK helper, containing a `forkedFrom` marker in its lines |
| Materialization tier | A session file's form of existence on A: `full` (complete copy), `stub` (summary shell), `unloaded` (record only, no file); an A-side disk-management concept, invisible to the protocol |

**Requirement-level convention**: **MUST** denotes a hard requirement for protocol correctness, **SHOULD** denotes the default requirement, **MAY** denotes a permitted option.

## 4. Sync unit and authoritative party

### 4.1 Sync unit: byte prefix, not a record list

The unit the protocol syncs is the **stable prefix** of the B file: the raw bytes in `[0, boundary)`, where `boundary` is the newline-terminated boundary. What goes on the wire is this byte range, not parsed records.

Why bytes rather than "lines" or "records": once fixed on bytes, three problems simultaneously become cheap — "did the content change" is one fingerprint computation, "where do I resume from" is reading one number, "did the tail get half-written" is looking at where the newline sits. The byte layer does not need to answer "which lines count"; that is the consumer's business.

The basis for the newline-terminated boundary: JSONL lines contain no newlines, so a line carrying a terminator was necessarily written out completely; a half-written line (claude output split across multiple writes, process dying between two writes) naturally falls outside the boundary. **A tail not terminated by a newline never belongs to any response** — boundary proves "the written part is not crossed", it does not prove "everything that should be written has been" (B cannot witness claude's in-process drain ordering; this is a declared boundary, see §11).

### 4.2 Verbatim copying

The only way A stores a copy is **verbatim copying**: new bytes are appended verbatim at the end; a whole-file restart is replaced verbatim. **No parsing, no deduplication, no field reordering, no re-serialization.**

This rule eliminates an entire class of failures. If A processed data before persisting (merging by uuid and rewriting), A's bytes would diverge from B's original, and the progress credential would have to become a two-sided mapping between "A's processed product" and "B's original" — complexity would spike. More critically, processing is exactly the source of the conflict between the two merge rules "keep first-occurring field" and "keep last-occurring field" — two interpretations of the same file necessarily diverge. Verbatim copying deletes the entire divergence path: A's file is byte-identical to B's prefix, and uuid-set comparability holds automatically. The lines worth keeping (all record lines, compact boundaries, bookkeeping lines, even malformed lines) are naturally inside the bytes and travel down with them; the sync layer does not adjudicate.

### 4.3 One authoritative party per file

At any moment each file has exactly one authoritative party, and ownership transfers over the lifecycle:

```text
[A creates fork]──A-managed──▶ publish confirmed ──▶ [B-managed]──claude grows──▶ A pulls incrementally
                                          │
                           either side deletes ──▶ [tombstone suppression] (must not rebuild)
```

- **B-managed**: the A-side copy may only be written by the sync process (append or whole-file replacement); a B-managed file is **never pushed back to B**.
- **A-managed**: exists only within the window "fork product written, publish not yet confirmed"; once confirmation returns, ownership transfers to B, all subsequent growth is produced by B, and A returns to incremental pulling; an A-managed file **is never overwritten by pulling before confirmation**.
- **Tombstone**: after a file is deleted, neither side may actively rebuild it; tombstones match by file instance (content fingerprint), and a new file with the same id is not suppressed by an old tombstone.

## 5. Cursor

### 5.1 What it is and the two jobs it does

A cursor is proof of "the prefix A has safely received", generated by B — only B can fingerprint B's file — while A holds and echoes it back as an opaque string. It does two jobs at once: **resume locator** (where do I continue from) and **consistency proof** (is the copy I got still your copy). Packing both uses into one value is the key to keeping "A stores only one string" in this protocol.

### 5.2 Encoding: three segments, each answering one question

```text
zpc1.<byte count>.<fingerprint>
```

Example: `zpc1.34567.d3c9f1a0e2b48c01a7f6e5d49b83021c`

| Segment | Question it answers | Value |
|---|---|---|
| `zpc1` | Which encoding version is this | Literal `zpc1`; unknown version → 400 |
| `34567` | How long a prefix have I seen | Decimal byte offset N; this cursor covers `[0, N)`; `0` = first pull; parsed as u64, overflow or non-digit → 400 |
| `d3c9f1a0…` | What is that prefix's content | Fingerprint of the raw bytes `[0, N)` (SHA-256 first 16 bytes, hex); **lowercase only**; length other than 32 or containing non-lowercase-hex characters → parse failure, treated as 400 |

Encoding requirements: three dot-separated segments, URL-safe character set, total length ≤ 80 characters (must fit in a GET query). The **zero-value cursor** (the canonical expression of first pull) is `zpc1.0.` followed by 32 `0` characters.

A may read the byte-count segment as a "length anchor" — comparing local file length before incremental writes, truncating by it after a crash — but **must not** interpret the fingerprint segment; all semantic judgment happens server-side.

### 5.3 Semantic rules

**The fingerprint doubles as file identity.** As long as prefix content changes (whole-file rewrite, delete-and-recreate, same-name switch), the fingerprint necessarily differs, and the old cursor's comparison automatically fails. This replaces every alternative criterion — inode, counter, timestamp. Inode produces false positives under "content-unchanged rewrite" (temp+rename swaps inode but bytes are identical); counters require B to add persistent state. The fingerprint is the only criterion that covers the "same uuid, different content" divergence.

**A bad cursor goes to 400, not whole-file restart.** Parse failure or unknown version must return an explicit 400. Why it cannot silently be treated as first pull: that would disguise corruption of A's own persisted cursor as "the server discovered divergence", triggering one pointless full rebuild while permanently masking the real fault point. **Corruption returns 400; divergence returns a whole-file restart; the two must not disguise as each other.**

**Monotonic within a file.** Within a single file instance the cursor byte count advances monotonically; cursors with different fingerprint segments belong to different file instances, and comparing byte counts across instances is meaningless — this is the basis of `wait_cursor`'s comparison rule (RFC 0003 §7).

**The cursor returned by publish confirmation is the same thing as a pull cursor** — proof of "the prefix of this fork now persisted on B"; A stores it directly as sync progress to complete the ownership handover (§7.3).

## 6. The `changes` operation

### 6.1 Request

```text
GET /v1/store/sessions/{id}/changes?cursor=<cursor string>
Authorization: Bearer <token>
```

`changes` answers one question: "holding this cursor of mine, what does this session on B look like now?" It is an idempotent read: retries are naturally safe. When the `cursor` parameter is absent, an empty string, or the zero-value cursor (§5.2), it expresses **first pull**. The route sits inside the existing `{id}/` resource family, isomorphic to `GET …/messages`, and automatically inherits the Bearer middleware on the Router.

### 6.2 Response body

Successful responses are always 200, in two forms depending on "whether there are bytes to send"; the client demultiplexes by `Content-Type`:

**No bytes to send (`unchanged`)** — JSON body:

```json
{ "ok": true,
  "state": "unchanged",
  "nextCursor": "zpc1.<byte count>.<fingerprint>" }
```

**Bytes to send (`append`/`reset`)** — `Content-Type: application/octet-stream`, the body is the raw byte range, metadata travels in HTTP headers:

```text
HTTP/1.1 200 OK
Content-Type: application/octet-stream
X-ZP-State: append | reset
X-ZP-Next-Cursor: zpc1.<byte count>.<fingerprint>
Content-Length: <byte count>

<raw byte range, emitted directly as body>
```

| Field/header | Semantics | Rules |
|---|---|---|
| `state` / `X-ZP-State` | Three-way verdict: **no change / new bytes / void — restart** | Required |
| body | The raw byte range to write into the mirror this time | The response body for `append`/`reset`; no byte range for `unchanged` (the verdict field lives in the JSON body) |
| `nextCursor` / `X-ZP-Next-Cursor` | The new stable-prefix credential covering the state after body is applied | Returned under every reply; for `unchanged` it echoes the original cursor |

**Why not JSON + base64 when there are bytes**: for `reset` (first pull) the body is the whole file — once a session accumulates to several MB, base64's 33% inflation and one extra text parse are real money; raw bytes cost zero inflation, and the client can write to disk as it receives, getting everything in one round trip. `unchanged` has no body to speak of, so JSON is the cheapest form; error responses are always JSON. The client distinguishes by `Content-Type`: JSON → parse the verdict field; `octet-stream` → read the header for the cursor, treat the body as bytes to write.

When the session does not exist, return **404** with a JSON error body:

```json
{ "ok": false, "error": "session <id> not found", "code": "missing" }
```

Semantically this is a fourth reply, "**absent on B**". It is expressed as 404 rather than a response field because absence is not a normal sync business branch — it carries no data and no progress, and the caller must go through classification rather than continue syncing; it is also isomorphic to `GET …/messages`' 404 precedent.

### 6.3 Server-side judgment order

The server judges in the order of the table below, returning on first hit. `boundary` is the newline-terminated boundary of the requested session file; `p` is the parsed two-part payload of the cursor.

| # | Judgment condition | state | body | nextCursor |
|---|---|---|---|---|
| 1 | cursor parameter absent/empty/zero-value | `reset` | `[0, boundary)` | `zpc1.boundary.H(boundary)` |
| 2 | cursor parse failure / unknown version | **400** | — | — |
| 3 | `p.offset > boundary` | `reset` | `[0, boundary)` | `zpc1.boundary.H(boundary)` |
| 4 | `fp(fd[0, p.offset)) != p.prefixHash` | `reset` | `[0, boundary)` | `zpc1.boundary.H(boundary)` |
| 5 | `p.offset == boundary` | `unchanged` | — | echoes original cursor |
| 6 | `p.offset < boundary` | `append` | `[p.offset, boundary)` | `zpc1.boundary.H(boundary)` |
| — | session file does not exist (including deleted) | **404** | — | — |

(`H(n)` denotes the fingerprint of the `[0, n)` prefix; judgments 3/4 may be swapped, both precede 5/6; **the session-existence check precedes the whole table** — if the file does not exist it is 404, no cursor judgment runs.)

**Judgment and range extraction must come from the same file snapshot.** claude is a filesystem-level writer, outside B's lock domain: if the prefix fingerprint check passes at T1 and the body is read at T2, and between the two reads the file is truncated and rewritten in place (not rename, fd does not migrate), the emitted body comes from the new file while A keeps the old prefix — the spliced hybrid still passes the server's fingerprint check, producing **permanent silent divergence**. The contract requires: the byte range emitted in the response and the prefix check must come from the same snapshot — after assembling the response and before sending it, the server re-`fstat`s and compares the `(size, mtime_ns)` recorded at request start; mismatch voids the whole attempt and retries; rename-style rewrites are naturally safe (fd pins the old inode), and in-place writers have only this one defense. The implementation is in RFC 0004 §4.

The four verdict branches each correspond to a real scenario; it is worth walking through each:

- **First pull (branch 1)**: A has no cursor (after new-session registration, after a new A comes online, after corruption rebuild); the entire stable prefix is returned. Note the body does not include the unterminated tail — if the file length is 5400 while boundary is 5350, only 5350 bytes are sent.
- **Prefix invalid (branch 3/4) → `reset`**. The two triggers differ semantically but reach the same conclusion: `p.offset > boundary` is "the prefix's length promise failed" — the file was truncated and rewritten or deleted and recreated, and the interval the cursor points at no longer physically exists; fingerprint mismatch is "the prefix's content promise failed" — typical triggers are B-side merge whole-file rewrite, or "same uuid, different content" divergence. Both mean A has no trustworthy retained segment, so the complete stable prefix is sent.
- **Caught up (branch 5) → `unchanged`**. boundary has not advanced past `p.offset` since it was last generated, i.e. no new complete lines. `nextCursor` echoes the original cursor — maintaining the single shape "every response advances interpretation", so client logic needs no special-case progress commit for unchanged. **`unchanged` must still pass the fingerprint check first**: a whole-file rewrite can keep the length the same while the content has changed.
- **Incremental (branch 6) → `append`**. body = one contiguous byte range `[p.offset, boundary)`, both endpoints on newline boundaries.

**The sole basis for server judgment is the prefix fingerprint.** File length, mtime, and inode may only serve as cache-invalidation hints (RFC 0004 §6); they must not be judgment criteria — B has external writers, these metadata are untrustworthy.

### 6.4 Client application rules

A applies results to disk per the table below. **The write-order iron rule precedes everything: mirror file data must complete fsync-level persistence first; the new cursor is committed into `state.json` only afterward**. Reversing the order makes post-crash progress overtake what was actually persisted — lying to the recovery logic.

| state | A-side action (strict order) |
|---|---|
| `unchanged` | Do not write the file; update the `lastUnchangedAt` observation field |
| `append` | ① Compare `local length == p.offset`; ② append body bytes at the end + fsync; ③ commit `X-ZP-Next-Cursor` |
| `reset` | ① body bytes → same-directory temp file `<sid>.jsonl.zp<PID>` + fsync; ② atomic rename to `<sid>.jsonl` + directory fsync; ③ **re-check tombstone**: on hit, delete the file and do not commit; ④ commit `X-ZP-Next-Cursor` |
| Short read / missing metadata header | Received octet-stream bytes < `Content-Length`, or either `X-ZP-State`/`X-ZP-Next-Cursor` header missing → **treat as transport error**: discard the temp artifact, do not commit the cursor, go through transport-layer retry. Partial append residue is caught by the next round's ① length comparison, converting to a whole-file re-pull — self-healing |
| 404 | **Do not create the file**; handle per RFC 0002 §6 classification; strictly forbidden to treat as `reset` — otherwise the local file would be emptied and then pushed back to B, resurrecting it |
| 400 | Local persisted cursor corrupted: explicit failure, handle per corruption semantics (RFC 0002 §8), no silent restart |
| 5xx / network error | Transport-layer retry (RFC 0003 §6.3); after exhaustion, back off and re-enqueue |

The `append` precondition comparison is the hot-path detection of "was local content modified": `local length != p.offset` means an external writer touched this B-managed file, the local prefix can no longer self-certify, and it must switch to whole-file re-pull. **The only means of forcing `reset` inside the protocol is the zero-value cursor** (§6.3 branch 1) — resending the request with `cursor=zpc1` (zero value) guarantees the server returns the full prefix; resending the same old cursor would again be judged `append`/`unchanged` because local mismatch does not affect the server's fingerprint check, looping forever.

The tombstone re-check in `reset` step ③ cannot be omitted: atomic rename is create semantics — if "delete session" arrives while the body is in transit, without the re-check the deleted file would be resurrected by the rename; on tombstone hit, discard the result, delete the file, and do not commit progress. Two supplementary declarations: ① **all step orderings in this table execute inside zonepaird's single-writer serial domain** (RFC 0003 §3.1); tombstone writes and pull persistence share the domain — this is the only closing condition for the "tombstone lands between re-check and commit" window; ② the re-check's match key is `(sid, deleted.fileId)`: `fileId` being null or equal to the file's fingerprint both count as hits — null recorded when the file was absent means "this id is not allowed to have a file again".

### 6.5 Full sequence

Normal incremental scenario:

```text
T0  A holds zpc1.4000.<h1>, local file length 4000
T1  claude on B wrote three more lines, file now 5400; boundary = 5350
    (the last 50 bytes are an unfinished line, excluded by the boundary)
T2  A → GET /v1/store/sessions/s1/changes?cursor=zpc1.4000.<h1>
T3  B: p.offset 4000 < boundary 5350; fp([0,4000)) == h1 passes
     → 200  Content-Type: application/octet-stream
            X-ZP-State: append
            X-ZP-Next-Cursor: zpc1.5350.<h2>
            <body = [4000,5350) raw bytes>
T4  A: local length 4000 == 4000 → append 1350 bytes at end + fsync
     → state.json commits cursor zpc1.5350.<h2>
```

Contrast scenario — whole-file rewrite on B: at T1 a merge happened instead of an append; the first 4000 bytes' content has changed. At T3 the fingerprint mismatches → `reset` + full `[0, 5350)`, and A goes through the temp-file + rename path. Same request, two replies; the criterion is always just the prefix fingerprint.

## 7. The `publish` operation

`publish` is the protocol's only A→B write: after the A-side fork produces a new session file, one request delivers it to B.

### 7.1 Request

```text
POST /v1/store/sessions/{id}/publish
Authorization: Bearer <token>
Content-Type: application/json

{
  "sessionId": "<id>",
  "content": "<complete jsonl bytes, encoding below>",
  "contentSha256": "<64-char hex, SHA-256 of the decoded content bytes>"
}
```

- `sessionId` must match the path's `{id}`; mismatch → 400.
- `content` is a one-shot delivery of the complete file. This is not incremental — the fork product is delivered wholesale. Encoding uses **base64 (RFC 4648 standard charset, with padding)**. publish uploads are rare anyway (once per fork), and keeping JSON-internal encoding gives the request body a single shape; if a fork product grows large enough that the inflation is noticeable, it can later switch to raw body upload in the same spirit as `changes` without changing the protocol shape.
- `contentSha256` lets the server verify transport integrity and doubles as the idempotency criterion (§7.2). **Lowercase hex only** — its first 32 characters go directly into the `zpc1` cursor's fingerprint segment (§5.2 lowercase-only); if upstream sends uppercase, the server would generate an illegal cursor and the next `changes` would necessarily 400.

The body uses raw bytes rather than a parsed JSON array: if B parsed and rewrote, "byte-verbatim delivery" would become "semantic delivery", adding a re-serialization drift surface (serde changing whitespace and field order), and `contentSha256` could no longer verify the persisted bytes. Server-side format validation needs only two rules: **every line ends with `\n`, and every line parses as JSON** — no line is ever rewritten.

### 7.2 Responses

| Server observation | Response | Semantics |
|---|---|---|
| File does not exist | `200 {"ok":true,"published":true,"already":false,"cursor":"<generated>"}` | Temp file + rename atomically creates it at `projects/lab/<id>.jsonl` |
| File exists and bytes identical to `content` | `200 {"ok":true,"published":true,"already":true,"cursor":"<generated>"}` | Idempotent replay: retries and queue resends are safe |
| File exists but bytes differ | `409 {"ok":false,"error":"conflict"}` | Terminal divergence: never merge, never overwrite, never return a merged result |
| Body unparseable / line validation fails / sha mismatch / path id≠body id | 400 | Caller error |
| Internal IO failure | 500 | Retryable |

The three success/failure branches correspond to three concrete timings: **first publish** — the fork produced session `abc`, absent on B → atomic create, `already:false`; **retry** — the last publish was persisted but the response was lost on the network, A resends the same body per queue semantics → bytes completely identical → `already:true`, treated as success and progress continues; **conflict** — same id, different content, possibly B already has that session or a half-finished residue → 409; the server attempts no merge, handing the "recover or abandon" decision back intact to A's task table.

Implementation order of the idempotency criterion: first compare `contentSha256` with the SHA-256 of the existing file's bytes; match → `already:true`; mismatch → 409. Identical sha means identical bytes (256-bit collision margin), no second byte-by-byte comparison needed.

**Premise declaration for the already criterion**: the byte-equality criterion relies on "no writes to that id on B before publish is confirmed" — the task phase machine (RFC 0002 §4) guarantees the fork product is not touched by claude before publish confirmation (it is not on B yet; nobody can write it). The residual race is declared honestly: if a publish's ack is lost and, while A retries, another writer on B appends to the same id (existing file = content + foreign tail), the retrier gets 409 rather than already — at that point A first runs a `changes` reconciliation before deciding, and does not treat a benign race as terminal divergence (RFC 0003 §6.3's 409 handling already parks it as `degraded(conflict)` without auto-retry).

### 7.3 Confirmation cursor: saving one round trip along the way

**All 200 responses must include `cursor`**, constructed as:

```text
cursor = "zpc1." + len(content bytes) + "." + first 32 chars of contentSha256
```

Two payload segments: byte count = content byte count, fingerprint = SHA-256 truncated over the content bytes (i.e. the first 32 characters of `contentSha256` — **a truncation of the same computation made for the request body; zero extra fingerprint cost on the server**). The `already:true` branch computes the same construction over the existing file on the spot.

A stores this cursor directly into `pull.cursor` to complete the ownership handover — "this fork's prefix now persisted on B" is the junction point, sparing the second round trip of "publish then send changes once more for a cursor". 409/400 responses carry no cursor.

Server-side format validation requires every line to end with `\n` (§7.1), so the cursor byte count always equals boundary; no extra convergence branch is needed. If validation is ever relaxed to allow an unterminated trailing line, that publish's cursor byte count would exceed boundary, and the next `changes` would naturally return `reset` per §6.3 branch 3 to converge — the protocol shape is unchanged; this is recorded here only.

### 7.4 Why publish does not reuse merge

The three semantics of the existing `PUT …/messages` (merge) are all wrong for fork delivery: merge does a uuid-based "keep first-occurring field" union, which would **silently glue two different contents** into one file, swallowing content divergence; merge discards incoming lines without uuid, while the fork product requires all lines preserved verbatim; merge normalizes the `sessionId` field, which amounts to inventing fork semantics a second time. The two are two different write families: publish is "declare complete content or detect conflict", merge is "incremental union"; they cannot substitute for each other. merge remains for the sess CLI's manual-intervention path (RFC 0004 §2.2).

### 7.5 Server-side atomicity

"Check existence → decide write/conflict" must execute under write-path mutual exclusion (same lock domain as merge/fork/delete, RFC 0004 §8). The ordering of concurrent writes to the same id is adjudicated by the lock: whoever gets the lock first is "the fact that happened first", and the later one correctly lands in the `already` or `conflict` branch — there is no third error state.

B does not perform "was this id ever deleted" tombstone checks — B stays free of persistent state; "do not publish rolled-back products" is guaranteed by A-side tombstones and the task table (RFC 0002). B's duty ends at faithfully reflecting "the relationship between the current file and the incoming content".

## 8. Error semantics summary table

| Scenario | Status code | Body | Client semantics | Retry |
|---|---|---|---|---|
| changes normal verdict | 200 | §6.2 | Apply per state | — |
| changes session missing | 404 | `{"ok":false,"error":…,"code":"missing"}` | B missing, enter classification | No |
| changes cursor corrupted | 400 | `{"ok":false,"error":"bad cursor"}` | Persisted cursor corrupted, explicit failure | No |
| changes/publish internal failure | 500 | `{"ok":false,"error":…}` | Transport-layer retry | Yes |
| publish success (first/idempotent) | 200 | `{"ok":true,"published":true,"already":…,"cursor":…}` | Advance per already | — |
| publish conflict | 409 | `{"ok":false,"error":"conflict"}` | Terminal divergence, hand to task table | No |
| publish caller error | 400 | `{"ok":false,"error":…}` | Fix and resend | No |
| Old server without this route | 404 | Empty/non-JSON body | Server too old, explicit failure (§9) | No |
| Timeout / connection drop | — | No complete response | Same class as network error, transport-layer retry | Yes |
| 401 / 429 | — | Router-layer middleware | Auth/rate-limit, inherits existing middleware contract; this protocol does not define | Per middleware |

**The 404 criterion is tightened to positive matching**: only `404 + parseable JSON + code=="missing"` counts as "session missing" and enters classification; every other 404 form (empty body, non-JSON, or a codeless JSON error page injected by a proxy/gateway) is judged "server too old" and fails explicitly. Loosening it even a little produces a real accident: if a gateway's JSON 404 were treated as "session missing", classification's worst case could tombstone the local file — mistaking someone else's error page for sync semantics is the most expensive misjudgment direction.

The uniform dividing rule: **recoverable verdicts inside normal flow go into 2xx response fields; terminal divergence and caller errors go to 4xx; retryable failures go to 5xx**. So `reset` is a 200 field (an expected business branch) while `conflict` is 409 (terminal); "B missing" is 404 (goes to classification) while "cursor corrupted" is 400 (goes to corruption semantics) — every error code has exactly one destination.

## 9. Version compatibility

| Direction | Behavior |
|---|---|
| Old client → new server | Pure new routes, zero impact; existing endpoint semantics unchanged |
| New client → old server calling `changes` | axum default 404 + **empty body**; judgment uses §8's positive criterion: "session missing" only accepts `404 + JSON + code=="missing"`; every other 404 is judged server too old and **fails explicitly prompting a B upgrade**. Silently degrading to exists+full GET is forbidden — silent fallback would re-invite the full-pull mode this design eliminates, and would make "incremental is live" a false observation |
| First pull (no cursor) | New server: empty cursor → `reset`; old server compatibility floor = one-shot `GET messages` pull (allowed: only "full pull every time" is forbidden, not one-time initial sync); incremental calls carrying a cursor have no downgrade |

**No capability-probe endpoint**: the 404 body shape of the first `changes` already gives the same signal for free; a probe endpoint is new public surface added to save one request, and during mixed-version periods it would become a fixed per-task overhead.

## 10. Protocol invariants summary

The invariants both sides must maintain are the protocol's compressed expression:

1. **Prefix equality**: A's verified prefix is byte-identical to B's prefix `[0, N)` (§5.1's two jobs serve this).
2. **Write order**: file data lands before progress commit; any progress advance happens only after its data completes fsync-level persistence.
3. **Monotonic within a file**: within a single file instance the cursor byte count advances monotonically; cursors with different fingerprint segments are not numerically compared.
4. **Conservative boundary**: `nextCursor` never exceeds the newline-terminated boundary; the unterminated tail never participates in sync.
5. **Fingerprint sole criterion**: server-side prefix-invalidation judgment relies only on the fingerprint; client-side local-integrity guarding relies only on the length anchor + reconciliation (RFC 0002 §7).
6. **Single authoritative party**: B-managed files are not pushed back, A-managed files are not overwritten by pulling, tombstoned files are not rebuilt.
7. **Corruption does not disguise**: bad cursor → 400, missing → 404, conflict → 409, divergence → `reset` — each semantic has a unique expression and they do not disguise as each other.

## 11. Known boundaries and security considerations

What the protocol explicitly does not do — all declared boundaries, not defects:

- **`nextCursor` only promises "does not cross safely-persisted content"**, it does not promise "everything claude should write has landed" — drain→persist ordering is a fact of claude's process lifecycle that B cannot witness; the protocol adds no field for it.
- **Deletion does not propagate**: A-side deletion produces a local tombstone; B adds no tombstone state; propagation of B-side deletion is an independent lifecycle need, outside this protocol's authorization.
- **A-side disk reclamation is not a protocol matter**: reclaiming local space after a session file grows is handled by materialization tiers (RFC 0002 §3, RFC 0003) — degrade to `stub`/`unloaded` and pull again when needed; `reset` semantics naturally cover both "deleted then re-pulled" and "converging after B trims", with zero B-side awareness and zero protocol change.
- **No pagination**: responses are always single bodies; the scale assumption is that a single session file is of the same order as the existing `GET messages` response. The extension point is already reserved: `nextCursor` is by definition an arbitrary legal position generated by the server; in the future the body can be truncated at any newline boundary with `nextCursor` stopped there, and the client continuing to pull with it is natural resume — the protocol shape need not change.
- **Auxiliary assets** (contents of the `<sid>/` directory) are outside sync scope.
- **Security surface**: the two routes inherit the Bearer middleware on the Router, adding no new auth surface; cursors are unsigned (the consequence of corruption is only reset; there is no security need); publish's atomic write + 409 refusal to silently overwrite prevents content gluing across writers.
